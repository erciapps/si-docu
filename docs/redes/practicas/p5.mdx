# Práctica 5. Control de acceso a servicios web con Keycloak y OAuth2-Proxy

## 1. Título
Configuración de autenticación centralizada con Keycloak y protección de servicios web mediante OAuth2-Proxy, diferenciando el acceso según el rol del usuario.

## 2. Resultado de aprendizaje y criterios de evaluación

### RA6. Opera sistemas en red gestionando sus recursos e identificando las restricciones de seguridad existentes
- **a)** Se ha configurado el acceso a recursos locales y recursos de red.
- **b)** Se han identificado y configurado los derechos de usuario y directivas de seguridad.
- **d)** Se ha accedido a los servidores utilizando técnicas de conexión remota.
- **e)** Se ha evaluado la necesidad de proteger los recursos y el sistema.
- **f)** Se han instalado y evaluado utilidades de seguridad básica.

## 3. Objetivos de la práctica
- Comprender el uso de un sistema de autenticación centralizada.
- Crear usuarios y roles en Keycloak.
- Proteger un servicio web mediante OAuth2-Proxy.
- Diferenciar el acceso a recursos según el rol asignado.
- Comprobar que un usuario accede solo a los recursos autorizados.
- Valorar la necesidad de proteger aplicaciones internas con autenticación.

## 4. Recursos necesarios
- Una máquina virtual o contenedor con Docker.
- Un servicio Keycloak en ejecución.
- Un servicio OAuth2-Proxy en ejecución.
- Uno o varios servicios web internos ya desplegados.
- Un proxy inverso si el profesor lo considera necesario.
- Un equipo cliente con navegador web.
- Acceso a terminal y a la interfaz de administración de Keycloak.

## 5. Escenario propuesto
Se dispone de una máquina con varios servicios web internos. El acceso a esos servicios no se realizará directamente, sino a través de un sistema de autenticación centralizado.

Se trabajará con dos perfiles de usuario:
- **admin**
- **empleado**

Se deben proteger, al menos, dos recursos:
- un recurso o ruta accesible solo para `admin`
- un recurso o ruta accesible para `empleado`

Ejemplo de rutas:
- `https://intra.local/admin`
- `https://intra.local/empleado`

También se puede plantear con dos servicios distintos:
- `admin.local`
- `empleado.local`

## 6. Desarrollo de la práctica

### Parte 1. Comprobación del entorno
1. Comprueba que los servicios necesarios están levantados:
   - Keycloak
   - OAuth2-Proxy
   - servicio o servicios web protegidos
2. Comprueba que el cliente tiene conectividad con la máquina servidora.
3. Verifica que puedes acceder a la consola de administración de Keycloak.

Comandos orientativos:
```bash
docker ps
ping 10.0.0.40
ss -tulpen
```

### Parte 2. Configuración inicial de Keycloak
1. Accede a la consola de administración de Keycloak.
2. Crea un `realm` o utiliza el indicado por el profesor.
3. Crea un cliente para OAuth2-Proxy.
4. Configura la URL de redirección autorizada.
5. Guarda la configuración y anota los datos necesarios.

Se deben identificar claramente:
- nombre del realm
- cliente creado
- URL de redirección
- credenciales o secreto del cliente, si procede

### Parte 3. Creación de usuarios y roles
1. Crea los roles necesarios:
   - `admin`
   - `empleado`
2. Crea, al menos, dos usuarios.
3. Asigna a cada usuario el rol correspondiente.
4. Establece una contraseña inicial y comprueba que cada usuario puede autenticarse.

Ejemplo:
- Usuario 1: `ana_admin` -> rol `admin`
- Usuario 2: `juan_empleado` -> rol `empleado`

### Parte 4. Configuración de OAuth2-Proxy
1. Configura OAuth2-Proxy para que utilice Keycloak como proveedor de autenticación.
2. Indica:
   - cliente
   - secreto
   - URL del proveedor
   - correo o dominio permitido, si procede
   - cabeceras necesarias
3. Configura el acceso al servicio o servicios internos.
4. Reinicia el servicio si es necesario.

La configuración debe permitir que el usuario no autenticado sea redirigido a Keycloak para iniciar sesión.

### Parte 5. Protección del recurso según rol
1. Configura el acceso para que:
   - el usuario con rol `admin` pueda acceder al recurso de administración
   - el usuario con rol `empleado` acceda solo a su recurso
2. Comprueba qué ocurre cuando un usuario intenta entrar en un recurso que no le corresponde.
3. Anota si el acceso:
   - se permite
   - se deniega
   - redirige a otra página
   - muestra error

### Parte 6. Verificación desde el cliente
Desde el navegador del equipo cliente:
1. Accede al servicio protegido.
2. Comprueba que se redirige al sistema de autenticación.
3. Inicia sesión con el usuario `admin` y verifica sus permisos.
4. Cierra sesión.
5. Inicia sesión con el usuario `empleado` y verifica sus permisos.
6. Comprueba que cada usuario accede solo a lo que le corresponde.

### Parte 7. Comprobación final
Responde y demuestra:
1. Qué función cumple Keycloak en esta práctica.
2. Qué función cumple OAuth2-Proxy.
3. Qué roles has creado.
4. Qué usuario tiene cada rol.
5. Qué recurso puede usar cada usuario.
6. Qué ocurre si un usuario intenta acceder a un recurso para el que no tiene permisos.
7. Por qué esta solución mejora la seguridad del sistema.

## 7. Evidencias que debe entregar el alumnado
La entrega debe incluir, como mínimo:

- Captura de los servicios levantados (`docker ps` o equivalente).
- Captura de la creación del cliente en Keycloak.
- Captura de los roles creados.
- Captura de los usuarios creados y su rol.
- Captura o fragmento relevante de la configuración de OAuth2-Proxy.
- Captura del acceso con usuario `admin`.
- Captura del acceso con usuario `empleado`.
- Captura o explicación de un intento de acceso no permitido.
- Respuestas breves a las preguntas finales.

## 10. Criterios de corrección rápidos
- Los roles deben estar correctamente creados y asignados.
- El acceso debe pasar por el sistema de autenticación.
- El usuario `admin` y el usuario `empleado` deben tener comportamientos distintos según su rol.
- Debe demostrarse al menos un acceso permitido y uno denegado o restringido.
- La entrega debe incluir evidencias suficientes y ordenadas.

## 11. Ampliación opcional
Para subir nota o profundizar:
- Añadir un tercer rol.
- Proteger un segundo servicio diferente.
- Configurar cierre de sesión centralizado.
- Analizar las cabeceras que recibe el servicio protegido tras la autenticación.
